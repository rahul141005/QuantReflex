## 0. Context and mission

QuantReflex is a vanilla-JS/CSS offline-capable PWA (no build step, global-IIFE modules dual-exported to `window` + `module.exports`) that trains Speed Aptitude (Quant, DI, LR) for Indian competitive exams. The user mandated complete localization into English + हिन्दी + मराठी at a Google/Duolingo quality bar: every user-facing surface, researched exam-book terminology (never machine translation), instant language switching with persistence, zero performance/layout regressions — all shipped as ONE complete public release behind a feature flag that stays OFF until the mandatory **Final Localization Certification** (Phase H) passes with **zero critical findings**. That certification requirement is recorded in `docs/BIBLE/DECISION_LOG.md` (ADR-111, "Final Localization Certification — MANDATORY GATE") and is binding: *no localization work is complete until it passes.*

Two language settings exist (user decision, locked): **appLanguage** (menus/buttons/chrome, read via `QRI18n.t()`) and **studyLanguage** (questions, solutions, Learn chapters, AI explanations, read via `QRI18n.tc()`). Changing App language defaults Study language to match unless the user has explicitly diverged them.

## 1. The immutable foundation (Phases A–C) — what exists and MUST be reused

Do not redesign, rename, or bypass anything in this section. Reference implementations are cited so you can copy their exact patterns.

### 1.1 Core i18n module — `main-app/js/i18n.js` (`window.QRI18n`)
- `ENABLED = false` (i18n.js:29) — the master flag. Its inline pre-paint twin `I18N_ON` lives in a `<head>` script in `index.html` (~line 21–32, after `window.QR_APP_VERSION`). `scripts/i18n.check.js` asserts the two stay in lockstep. QA override: `localStorage qr_i18n_preview = '1'` force-enables both channels.
- `t(key, params)` — appLanguage channel. `tc(key, params)` — studyLanguage channel. `{token}` interpolation. Plural values are objects `{ one: '…{count}…', other: '…{count}…' }` selected by `Intl.PluralRules` on **`params.count`** (i18n.js:82–117). Hindi treats 0 as `one` (CLDR).
- Fallback: hi/mr → en → the key itself, with one-time `console.warn` per missing key.
- `register(lang, catalog)` merges per-namespace objects into the catalog store; locale files are IIFEs calling it.
- `applyDom(root)` walks `[data-i18n="ns.key"]` (textContent) and `[data-i18n-attr="attr:ns.key;attr2:ns.key2"]` (attributes), stashing originals in `data-i18n-orig` so switching back to EN restores byte-identical text. **Current constraint: `data-i18n` elements must contain ONLY text** — Phase D extends this (see §3.4.2).
- `localeTag()` → `en-IN` / `hi-IN-u-nu-latn` / `mr-IN-u-nu-latn` (`-u-nu-latn` pins digits to 0-9; never remove it — CLDR `mr-IN` otherwise renders Devanagari numerals).
- `onChange(cb)` subscribers fire on language change (used by stats fingerprint bust and `LearnView.invalidateHub()`).
- `setLanguages(app, study)` coerces both to `'en'` while `ENABLED` is false and preview is off — this is how EN behavior stays byte-identical pre-launch.

### 1.3 The enforcement harness — `main-app/scripts/i18n.check.js` (runs inside `npm test`)

Seven sections: (1) flat key-set parity en/hi/mr + no empty values + plural-category parity; (2) `{token}` placeholder parity; (3) **no-Latin-leakage** in hi/mr values — after stripping `{tokens}`, HTML tags, and `LATIN_ALLOWLIST` (i18n.check.js:34–41: QuantReflex, QuanAI, Premium, English, DI, LR, AI, exam acronyms, km/kmph/cm/mm/kg, XP, Google, Speed Aptitude, Speed Score, Math Duel, Quant, theme names, product URLs, etc.), any `/[A-Za-z]{3,}/` match fails; (4) every `data-i18n`/`data-i18n-attr` key in index.html resolves in all three catalogs (mechanism at i18n.check.js:114–132 — regexes `/data-i18n="([^"]+)"/g` and `/data-i18n-attr="([^"]+)"/g`, attr values split on `;` then after the first `:`); (5) flag lockstep (`I18N_ON` ⇄ `ENABLED`) + SW precache + script-tag load order; (6) t/tc channel-separation source scan; (7) runtime behavior tests via `require()` with cache-delete + `global.localStorage` stub (flag-off coercion, preview switching, fallback, hi plural 0=one, locale tags).

## 2. Global invariants for Phases D–H

1. **The flag stays OFF until Phase H exit.** No milestone flips `ENABLED`/`I18N_ON`.
2. **Machine data never translates**: ids, `subtype` strings (`'medium:divide'`), `related[]` topic ids, `expr` formula strings, deep-link hashes, category keys, chart-spec field NAMES, Firestore field names, error codes, `chip.value`, localStorage keys.
3. **Separator contracts**: drill-engine splits explanation strings into steps on `→`, `;`, and newline (`_explainSteps`). Translated explanations MUST keep `→` as the step separator and must NOT rely on `।` for splitting. The `diff:key` subtype prefix contract is untouched.
4. **Digit preservation**: every translated stem/explanation must contain the SAME multiset of digit tokens as its EN twin (0-9 only, never Devanagari numerals). Mechanically enforced in Phase F (§5.7).
5. **Node-require safety**: every new runtime file is a global-IIFE with dual export and must not touch `document`/`localStorage` unguarded at parse time (check scripts `require()` them with stubs).
6. **`shared/` is outside the deploy root** (ADR-099): never reference `../shared` from runtime code; same-origin copies only.
7. **Known-limits register**: `docs/BIBLE/I18N_KNOWN_LIMITS.md` is created in Phase D and appended to in every phase — the single authoritative list of intentionally-English/intentionally-frozen items, each with a rationale. Phase H certifies against it: anything English NOT in this register is a critical finding. (Seed list in §7.3.)

### 3.4 Architecture

**3.4.1 English stays inline in index.html** (established Phase A decision — the HTML is the EN source of truth; hi/mr overwrite via `applyDom`). Rejected alternative: extracting EN into the catalog and rendering all languages from keys — rejected because it churns 200+ lines of fact-checked EN copy (ADR-110), risks EN regressions while the flag is off, and breaks the EN-byte-identity verification model.

**3.4.2 Mixed-markup strategy — `data-i18n-html` (REQUIRED new capability).** About/Guide bodies embed `<strong>` mid-sentence, so sentences cannot be split into text-only spans without producing untranslatable fragments (hi/mr word order differs — a fragment like "the ability to" cannot be translated in isolation). Decision:
- Extend `applyDom`: an element bearing **`data-i18n-html="ns.key"`** gets its `innerHTML` replaced by the catalog value after a **whitelist sanitizer**: parse the value in a detached `<template>`, walk it, unwrap (keep text of) any element whose tag is not in `{STRONG, EM, BR}`, and strip ALL attributes from allowed tags. Stash the original `innerHTML` in `data-i18n-orig-html` for EN restore. Missing key → leave the element untouched (EN fallback = original markup). Safe because values come exclusively from in-repo, leak-checked catalogs (check section 3 already strips tags before its Latin heuristic, so `<strong>` inside hi values passes).
- Icon-prefixed headings (`<h3><span class="qr-ico">…</span> Title</h3>`): do NOT use html mode. Wrap the trailing text in a plain `<span data-i18n="ns.key">Title</span>` — text-only; icon untouched. Same pattern for the contact card (keep the `<a>` outside the tagged span).
- `<li>` containing a premium chip: restructure minimally so the chip is a SIBLING of the tagged span (`<li><span data-i18n-html="…">text…</span> <span class="info-premium-chip">…</span></li>`); the chip's own label gets its own `data-i18n`.
- Extend `i18n.check.js` in the SAME milestone: section 4 gains a third regex for `data-i18n-html="…"`; plus a static safety scan asserting every hi/mr value of any key used in a `data-i18n-html` attribute contains no tag outside the whitelist (regex `<(?!\/?(strong|em|br)\b)[a-z]`) and has balanced strong/em tags.
- Rejected alternatives: (a) arbitrary HTML in catalog values without sanitizing — one bad value becomes an injection/regression vector the certification cannot bound; (b) rebuilding About/Guide from JS templates — needless churn of certified ADR-110 content; (c) per-fragment keys around `<strong>` — untranslatable fragments, see above.

**3.4.3 Key naming.** `about.*`: `heroTitle, heroSub, closeAria, s1Title, s1P1…s1P3, s2Title, s2Li1…s2Li5, s3Title, s3Li1…s3Li7, s4Title, s4P1, s4P2, s5Title, s5Status, s6Title, s6Version, s6Update, s6P1, s7Title, s7Name, s7P1, s8Title, s8CardTitle, s8CopyAria, s8CopyTitle, s9Title, s9P1, quote`. `guide.*`: `heroTitle, heroSub, closeAria, tocAria, toc1…toc16`, then per section `s<N>Title, s<N>H4_1…, s<N>P1…, s<N>Li1…` in document order (sections numbered 1–16 exactly as the TOC id order above). Positional keys are acceptable here because the EN source of truth is the HTML itself and the check cross-validates existence; semantic names add no safety. The email address and `KrisVeltrix (KVt)` stay inside translated strings verbatim (DNT).

**3.4.4 Duel UI.** Pure key-swap through a module-local guarded `_t/_tx` (pattern from duel-manager.js). All strings live in the existing `duel` namespace. Compositions become parameterized keys. **Mandatory reuse** (do not mint duplicates): difficulty labels → `settings.difficultyEasy/Medium/Hard`; `Timer`/`Per Ques.`/`Total`/`seconds` → `practice.timer/perQues/total/seconds`; `You will solve {v} questions` → `practice.youWillSolve` (plural); category labels → `formatCategoryName`; `Cancel` → `modals.cancel`; `Draw`/`{name} wins`/`You`/`Opponent` → `share.draw/wins/you/opponent`; `✓ Correct` → `drill.correct`; `Your answer`/`Correct answer` → `drill.yourAnswer/correctAnswer`. ### 5.4 Architecture

**5.4.1 Core principle — separate math from surface.** Each archetype's `build()` stops composing strings and instead returns a language-neutral result: `{ slots, a, k, options?, v }` where `slots` = named values (numbers, name-pool indexes, theme/pool indexes, computed intermediates), `v` = ONE variant seed drawn as `randInt(0, 999)`. A new registry renders the surface: `QRGenI18n.render(engine, archKey, v, slots)` → `{q, explain}` by resolving the active study-language pack's template list for `archKey` and using `templates[v % templates.length]`. EN packs contain the CURRENT strings extracted verbatim (each legacy `pick([t1,t2])` branch becomes a template array entry). Language resolution happens entirely inside `render()` with ZERO random calls (enforced: the check stubs `Math.random` to throw during render) — so for a fixed RNG seed, slots/answers/options are IDENTICAL in every language by construction.
Rejected alternatives: (a) per-language full builder forks — 3× the math code, divergence guaranteed, answer invariance unprovable; (b) post-hoc string translation of EN output — machine-translation quality, breaks digit order, grammatically impossible for gender/SOV; (c) requiring equal variant counts per language — forces 300+ artificial hi variants; the `v % length` rule keeps RNG consumption identical while letting each language ship 1..n variants.

**5.4.2 Registry + loader.** `js/gen-i18n.js` (`window.QRGenI18n`): `register(lang, engine, pack)` where `pack = { pools: {…}, tpl: { archKey: { s: [fn(slots)…], e: [fn(slots)…] } } }`; `render(engine, key, v, slots)` resolves active studyLanguage (via a boot-time hook to QRI18n; guarded default `'en'`), falls back per-archetype to EN with a one-time `console.warn`; `pools(engine)` accessor for engines that need pool sizes. `js/i18n-packs.js` (`window.QRPacks`): `ensure(lang, cb)` idempotently injects `<script>` tags for that language's gen packs (and Phase G content packs later); called at boot for the active studyLanguage and inside the settings language-change path BEFORE view re-render. EN packs are EAGER (regular script tags — the engines' templates live there now); hi/mr packs LAZY but SW-precached (offline in any language). All 13 new files → index.html script list (en packs) / loader (hi, mr) + SW `ASSETS`; i18n.check section 5 extended accordingly.

**5.4.3 Trilingual name pool.** `QRGen.NAMES` (generative-helpers.js:40–43) becomes `[{en:'Ravi', hi:'रवि', mr:'रवी', g:'m'}, {en:'Priya', hi:'प्रिया', mr:'प्रिया', g:'f'}, …]` for all 24 entries (gender split ~12/12); `name()`/`twoNames()` return ENTRY OBJECTS; slots store them; EN templates emit `.en`, hi `.hi`, mr `.mr`. lr-engine's separate 32-name pool merges into the same structure (an `LR_NAMES` extension of the shared pool, single file). Every EN template extraction updates `nm[0]` → `slots.p1.en` mechanically.

**5.4.4 Grammar engineering rules (binding for template authors).**
- *Hindi*: perfective transitive verbs agree with the OBJECT (`रवि ने किताब खरीदी`) — object gender is fixed per template, so bake the verb form into the template; subject-agreeing forms (intransitive/future/imperfective) use the pack helper `g(p, m, f)` (e.g. `g(slots.p1,'गया','गई')`); named actors take non-honorific 3rd person (exam-book convention); the student is addressed as आप. Postpositions (ने/को/से/का-के-की) are written into templates, never concatenated generically.
- *Marathi*: perfective transitive agrees with object (`रवीने पुस्तक विकत घेतले`); intransitive past agrees with subject via `g(p,'गेला','गेली')`; तुम्ही-form for addressing the student; Target-Publications register.
- Numbers, `₹`, `%`, ratios (`2 : 3`), units (`km/h`, `m/s`, `cm`) appear EXACTLY as in EN — never respelled, never Devanagari digits. Explanations keep `→` as the step separator (global invariant 3) and may use `।` only WITHIN a step.
- *Syllogisms* (hi, per R.S. Aggarwal Hindi edition): `सभी A, B हैं` / `कोई A, B नहीं है` / `कुछ A, B हैं` / `कुछ A, B नहीं हैं`; (mr): `सर्व A हे B आहेत` / `कोणताही A, B नाही` / `काही A, B आहेत` / `काही A, B नाहीत`. The 40-noun pool translates per language (plural-neutral forms).
- *Blood relations*: Hindi/Marathi kinship is MORE SPECIFIC than English (uncle → चाचा/मामा/ताऊ/फूफा by lineage). Refactor the relation composition (`_compose2`) to produce stable RELATION IDS (e.g. `mothers_brother`, `fathers_father`), with per-language id→term maps; the EN map reproduces today's strings exactly. This is the single highest-correctness-risk area → dedicated truth-table test (F-M6): enumerate EVERY composable pair, assert against a hand-written expected table per language (glossary-sourced: मामा=mother's brother, चाचा=father's younger brother, दादा=paternal grandfather, नाना=maternal grandfather, etc.; Marathi: मामा, काका, आजोबा distinctions).
- *Directions/calendar*: hi उत्तर/दक्षिण/पूर्व/पश्चिम + उत्तर-पूर्व compounds; weekdays सोमवार… / months जनवरी…; mr same-script equivalents (जानेवारी…).
- *Coding–decoding*: the cipher substrate (Latin letters/words, e.g. `CAT → DBU`) STAYS Latin — Hindi exam books keep the English alphabet for letter-shift puzzles. Stem prose translates around it. The generated-output leak heuristic therefore allowlists all-caps Latin tokens `/^[A-Z]{2,}$/` (§5.4.6).
- *Analogies / odd-word*: per-language AUTHORED quads and word groups, culturally adapted (hi: `हाथ : दस्ताना :: पैर : मोज़ा`), **index-aligned** with the EN pools — same array lengths, entry i in hi corresponds semantically to entry i in EN; the answer is stored as an INDEX in slots and rendered per language.
- *DI themes*: brands/cities transliterate to Devanagari (फ्लिपकार्ट, अमेज़न, जिओ; दिल्ली, मुंबई); metric/unit words translate (बिक्री, उत्पादन); per-language theme pools are index-aligned with EN; `_plural` remains EN-only (hi/mr pool entries carry their own singular/plural/oblique forms baked into template words). Chart titles/axis labels/series names/table columns flow from the localized pools into the chart spec — di-charts.js needs zero changes.

**5.4.5 Answer semantics per question type.** Numeric answers: identical numbers across languages (asserted). Text-MCQ answers (analogy, odd-word, blood-relation terms, syllogism verdicts, inequality verdicts): the ANSWER IS a language-dependent string — correctness is preserved structurally: slots carry the answer INDEX into an index-aligned pool; `_mcq` builds options from the same indexes; the check asserts (a) pool length parity across languages per pool, (b) for a fixed seed, the answer INDEX and option INDEX SET are identical across languages. Grading is unaffected (drill compares the rendered option strings, which are self-consistent within a language). Review-mode replays store rendered strings (§5.4.7) so a stored question grades against its own stored options.

**5.4.6 The Phase-F harness — `scripts/gen-i18n.check.js`.** Node-run, in npm test. Machinery: (1) seeded LCG stubbed over `Math.random`; (2) **masked-template census** for EN-identity: BEFORE each refactor batch, generate 5,000 questions per category on the legacy code and store the SET of digit-masked shapes (`replace(/\d+/g,'#')` on stem+explanation) in a fixtures file; AFTER, regenerate and assert set equality (RNG-stream-independent, catches any wording drift); (3) **cross-language answer invariance**: for every archetype key × difficulty, run with seed S in en, then hi, then mr — assert `{answer, options-index-set (or option multiset for numeric), category, subtype}` deep-equal and slots deep-equal; (4) **digit-multiset equality**: hi/mr stem+explanation contain exactly the EN twin's digit-token multiset; (5) **output leak heuristic**: generated hi/mr text, after stripping digits/units/₹/%/DNT allowlist/all-caps cipher tokens, must contain NO `/[A-Za-z]{3,}/`; (6) **render purity**: `Math.random` throws inside `render()` — any template calling it fails; (7) **separator rule**: every hi/mr explanation containing `→` in EN contains ≥ the same number of `→`; (8) coverage parity: every EN `tpl` archetype key exists in hi and mr packs (100% before Phase H — the check FAILS on gaps once a language's pack declares itself complete via a `complete: true` flag; during authoring, incomplete packs run in fallback-warn mode and the check reports remaining-gap counts).
`scripts/quant-engine.check.js` gains one line pinning node-context generation to EN (assert the engine's active language is `'en'` when `QRI18n` is stubbed off) — its digit-order recompute continues to validate EN math exactly as today. `subjects.check.js`, `di-engine.check.js`, `lr-engine.check.js` remain untouched and must stay green after every batch.

**5.4.7 Mistake archive & review mode (product decision, made now).** Generated question objects gain a `gen: { engine, k, v, slots, lang }` field (added in `_wrapArch` and the DI/LR wrappers; excluded-from-replay context categories at questions.js:1078 keep their exclusion). `progress.js` stores it with the mistake (cap-100 unchanged). Review replay (`generateMistakeReviewQuestions`): if `gen` is present and the CURRENT studyLanguage differs from `gen.lang`, re-render stem/explanation (and index-based options) via `QRGenI18n.render` from the stored slots — same math, current language. If `gen` is absent (mistakes captured before this phase), replay the frozen strings verbatim → known-limits entry: “mistakes recorded before the language feature render in the language they were practiced in.” Rejected: regenerating fresh questions (loses the exact mistake — product regression); translating stored strings (machine translation — banned).
